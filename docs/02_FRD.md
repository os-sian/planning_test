# 카페 판매·손익·재고 관리 기능 요구사항 문서(FRD)

작성일: 2026-10-12  
상태: v1. PRD의 합의 사항과 사용자의 “모두 추천대로” 지시를 반영한 기능·계산·예외 처리 기준.

FRD는 사용자가 무엇을 하면 프로그램이 어떤 일을 하고 어떤 결과를 보여 주는지 설명하는 문서다. 이 문서만으로 기능을 이해할 수 있도록 입력 항목, 계산, 저장 결과, 오류 동작을 함께 정리한다. 실제 프로그램을 구현하거나 시안을 수정한 결과는 아니다.

## 1. 근거와 결정의 구분

검토한 문서와 시안:

- `docs/01_PRD.md`: 1차 필수 기능 M1~M9, 사용자 선택, 2차 범위.
- `design/artisan_ledger/DESIGN.md`: 공통 표시·입력·모바일 표현 지침. 이 문서의 예시 기능을 신규 요구로 간주하지 않는다.
- `design/_1/code.html`, `design/_1/screen.png`: 일별 판매 기록과 새 판매 등록 창.
- `design/_2/code.html`, `design/_2/screen.png`: 메뉴 수익성과 등급, 상세 원가 창.
- `design/_3/code.html`, `design/_3/screen.png`: 일·월 실적 및 손익.
- `매장운영데이터/데이터설명.md`, `매장운영데이터/매장운영데이터.json`: 기록의 의미와 계산 입력 자료. 엑셀과 JSON은 같은 원천 기록이다.

이 문서의 기준은 다음처럼 구분한다.

| 구분 | 의미 |
| --- | --- |
| PRD 합의 | 사용자와 이미 정한 1차 기능·사용 범위 |
| 자료 사실 | 파일에 실제로 들어 있는 항목과 기록 의미 |
| 추천 채택 | 이번 요청에서 사용자가 남은 사항을 추천대로 정하도록 위임하여 채택한 기준. 원자료의 사실이나 업계 표준이라는 뜻은 아님 |
| 미정·범위 밖 | 별도 확인 없이 추가할 수 없는 기능 또는 구현 때 확인할 외부 조건 |

PRD에서 계산식·상세 동작을 제외한 것은 PRD 작성 범위에 대한 제한이었다. 이번 FRD 요청에 따라 계산 방법과 동작을 구체화한다. PRD의 필수 기능은 제거하지 않는다.

## 2. 프로그램의 범위와 핵심 흐름

**PRD 합의:** 본인 한 명이 컴퓨터·휴대폰 등 여러 기기에서 같은 매장 기록을 사용한다. 본인 외에는 조회·입력·수정·삭제·백업·복원할 수 없다.

1차 기능은 기존 자료로 시작, 판매·비용 입력/수정/삭제, 운영비 부담을 포함한 메뉴 수익성과 평가 등급, 일·월 손익, 입고·폐기·실제로 센 재고 기록, 이미 떨어진 재료 확인, 저장·전체 백업·복원이다.

사용 흐름: 본인 확인 → 판매 날짜·메뉴·채널·수량 입력 → 저장 → 메뉴별 남는 금액과 등급 확인 → 같은 기간의 손익 확인 → 기준일의 재료 잔량 확인 → 필요하면 입고·폐기·실측 재고 기록 → 전체 기록 백업.

단위는 원·부가세 제외, 판매수량은 메뉴별 개수, 재료는 g·ml·개다. 음료와 디저트가 함께 있으므로 전체 판매수량을 모두 “잔” 또는 “주문 건수”로 표시하지 않는다. 기록 한 줄은 날짜·메뉴·매장/포장별 판매 집계다.

**추천 채택:** 1차는 제공 자료의 한 매장을 대상으로 한다. 다른 매장 추가나 직원 계정 관리는 포함하지 않는다. 배포할 서비스와 본인 확인에 사용할 실제 계정은 아직 미정이며 구현 착수 시 확인한다.

## 3. 시안과 PRD의 차이 및 처리

| 시안에서 확인한 내용 | 차이 또는 문제 | FRD 반영 |
| --- | --- | --- |
| 판매·메뉴 수익성·손익 3개 상세 화면 | 재고·비용·백업/복원은 이동 메뉴만 있고 상세 화면이 없음. 본인 확인도 없음 | 없는 필수 기능은 F01·F05·F08~F11에 정의. 상세 시안 보완 필요 |
| 판매 날짜 입력칸은 목록에 있고 등록 창에는 날짜 표시만 있음 | 과거 날짜를 입력·수정하는 경로가 부족 | 선택한 날짜를 등록 창에 넘기고, 등록·수정 시 날짜 확인/변경 제공 |
| 등록 창에 채널·메뉴·수량·할인만 있음 | 당시 단가 수정, 실제 수수료 입력이 없음 | 기존 판매 관리에 필요한 단가·수수료 입력칸 추가 정의. 별도 신규 기능이 아님 |
| 시안 라떼 단가 4,500원 또는 5,000원, 원두 18g·우유 180ml | 자료의 메뉴 기준가 4,800원, 레시피 원두 20g·우유 200ml와 다름 | 표시용 예시를 데이터로 쓰지 않음. 실제 메뉴·레시피·당시 기록으로 대체 |
| 스무디·디카페인 옵션·콜드브루 등 시안 메뉴 | 자료의 8개 메뉴와 다른 목록 | 메뉴는 제공된 8개 ID와 이름을 사용. 메뉴 추가·옵션 관리는 2차 |
| 제조시간·점유면적·기기 전력으로 운영비 배분 | 관련 기록이 없고 PRD에서도 방식 미정 | 추천 채택 기준인 일별 순매출 비중 배분 적용. 제조시간 등 새 입력 기능 추가 안 함 |
| S 60% 이상, A 45~59%, B 30~44%, C 30% 미만 | 시안의 예시이며 합의된 등급 기준이 아니었음. 소수점 구간도 불명확 | C07의 채택한 기준으로 대체. 시안의 수치를 그대로 확정하지 않음 |
| 판매 미리보기의 “순마진율” | 수수료·운영비가 빠진 재료비 기준 비율임 | “등록 전 매출·재료 사용 미리보기”로 표현. 최종 수익성은 저장 후 해당 기간 전체로 계산 |
| 일별/월별 버튼 | 현재 HTML은 버튼 모양만 바꾸며 실제 집계 전환은 없음 | F06의 실제 날짜·월 집계 전환 구현 필요 |
| 등록·백업 완료 문구, PDF·엑셀 생성 알림 | 일부는 시간 경과 또는 알림만 있고 실제 저장·파일 생성 근거 없음 | 실제 저장 성공·파일 생성 확인 전에는 완료로 표시하지 않음 |
| 카드·표 합계가 서로 다름 | 판매 화면의 순매출 카드와 소계 등 예시 숫자 불일치 | 같은 조회조건의 원기록에서 계산. 필터 전·후 합계를 명시 |
| 판매시간, 주문수·객단가, 목표 달성률·손익분기점 | 원자료에 주문·시각·목표·손익분기 기준 없음 | 1차에서 미표시. 날짜·판매수량·계산 가능한 실적만 표시 |
| POS·센서 연동, 20시 자동 백업, 22시 자동 정산 | PRD에 없는 기능이거나 2차 항목 | 1차 제외. 연결 완료·자동 실행 문구도 제거 대상 |
| 제조 조언, 할인 금지·텀블러 할인, 세척·감가상각 상세, 고정 수수료 1.25%·로스율 14% | 자료에 없는 정책·비용·계산 가정 | 채택하지 않음. 임의 비용·할인 정책으로 계산하지 않음 |
| 리포트 인쇄/PDF, 원가표·판매·손익 Excel/CSV 내보내기 | 전체 백업과 다른 기능이며 PRD 1차에 없음 | 1차 제외. 필요한 경우 별도 확인. 전체 JSON 백업으로 자동 대체했다고 설명하지 않음 |
| 레시피 단가 수정 | 기준정보 편집은 2차 | 1차 상세 창은 읽기만 제공. 수정 버튼 제외 |
| 오늘 판매 마감, 지출 결의서, 백업 이력, 시스템 설정 | 마감 업무·결재·이력·설정 기능이 1차로 합의되지 않음 | 1차 제외. “입력하기”는 판매 등록으로, 비용 메뉴는 기존 비용 관리로 연결. 별도 결재나 자동 마감 추가 안 함 |
| 실거래 정합성 100%, 무결성 100% 문구 | 가상 샘플이며 검사 근거도 없음 | 삭제 대상. 실제 확인한 오류·기록 범위만 표시 |

시안 파일 자체는 이 작업에서 변경하지 않는다. 시안의 추가 기능은 버튼이 있다는 이유만으로 개발하지 않는다.

## 4. 채택한 운영 기준

아래는 사용자의 “모두 추천대로” 지시에 따라 채택한 추천안이다. 개별 선택을 사용자가 직접 답했다고 기록하지 않는다.

| 번호 | 기준 | 추천 이유 |
| --- | --- | --- |
| D01 | 운영비는 각 날짜의 메뉴별 순매출 비중으로 배분하고, 월은 일별 결과를 합산 | 할인과 당시 가격을 반영. 메뉴 검색에 따라 배분이 바뀌지 않으며 일·월 합계 연결 가능 |
| D02 | 비용기록의 8개 항목을 운영비로 포함. 월비용계획은 실적 비용에 더하지 않음 | 이미 있는 실제 기록을 관리하며 계획·일별 비용 중복 방지 |
| D03 | 과거 판매의 원가·수수료는 기록값 보존. 새 판매의 원가는 판매일의 가격 이력과 레시피로 산출, 수수료는 기록 전체의 실제 금액을 직접 입력 | 근거 없는 고정 수수료율을 쓰지 않고 과거 기록 보존 |
| D04 | 같은 날짜·메뉴·채널의 판매 집계는 한 줄. 추가 등록 시 중복을 알리고 기존 줄 수정으로 안내 | 같은 판매를 두 번 기록하는 위험 감소 |
| D05 | 재고는 기준일까지 전체 기록을 반영한 마감 기준 잔량. 실측 재고는 해당 날짜 마지막의 실제 수량으로 반영 | 시각 정보 없이 일별 자료를 일관되게 해석 |
| D06 | 재고 0은 소진, 음수는 소진과 기록 차이 확인 필요. 판매 입력은 허용하되 경고 | 이미 발생한 판매를 재고 기록 부족 때문에 누락시키지 않음 |
| D07 | 등급은 운영비 부담 후 수익률 기준 S/A/B/C, 경계는 C07에 정의 | 기존 시안의 등급 표현을 활용하되 적자와 낮은 수익을 구분하는 단순 기준 |
| D08 | 전체 백업은 JSON 파일, 복원은 전체 교체. 검증·내용 확인·최종 확인 후 적용 | 모든 연결 기록과 계산 기준을 함께 보관. 병합 중복 방지 |
| D09 | 저장 성공 시 같은 기록을 다른 기기에서 조회 가능. 같은 기록을 두 기기에서 바꾼 경우 늦은 저장을 막고 최신 내용 확인 안내 | 다른 기기의 변경을 조용히 덮어쓰지 않음 |
| D10 | 저장 실패·접근 실패·복원 오류는 기존 저장 기록 유지. 계산 근거가 빠지면 해당 결과를 “계산 불가”로 표시 | 실패를 성공이나 0원처럼 오해하지 않게 함 |

D03의 단가 입력과 수수료 입력, D05의 실측 입력 등은 PRD 필수 기능을 수행하기 위한 항목이다. 별도의 주문 관리·수수료 설정 화면·오프라인 관리·자동 백업 기능은 추가하지 않는다.

## 5. 모든 기능에 적용할 공통 동작

- 날짜는 한국 날짜 기준으로 해석한다. 저장 시각이 있더라도 판매 집계 날짜를 바꾸지 않는다. 입력 날짜는 초기재고 기준일인 2025-07-01 이전일 수 없다.
- 새 기록 날짜는 2026-09-18 이후도 허용한다. 자료 마감일을 프로그램 사용 종료일로 취급하지 않는다. 미래 날짜의 실적 입력은 막고, 미래 계획 입력은 1차에 없다.
- 이미 영업달력에 있는 영업·마감 상태는 원자료대로 보존한다. 새 날짜의 판매를 한 줄 저장했다고 그날 전체가 마감됐다고 처리하지 않는다. 새 날짜의 집계는 “입력 기록 기준·마감 미확인”으로 표시한다. 영업달력 편집·마감 전용 업무는 추가하지 않는다.
- 빈칸은 미입력, 0은 실제 0으로 구분한다. 필수 값이 빠지면 저장하지 않고 해당 입력칸과 이유를 보여 준다.
- 값 입력·조회·취소만으로 저장 기록을 바꾸지 않는다. 화면 필터와 검색도 기록 자체를 변경하지 않는다.
- 저장·수정·삭제는 관련 집계와 재고까지 함께 일관되게 반영되어야 한다. 일부만 반영되면 성공으로 표시하지 않는다.
- 처리가 끝나기 전 저장 버튼을 다시 눌러도 같은 변경을 두 번 적용하지 않는다. 결과를 알 수 없는 통신 실패 후에는 저장 여부를 먼저 확인한다.
- 취소·닫기 시 미저장 입력이 있으면 버릴지 확인한다. 계속 입력을 선택하면 값을 유지한다. 저장 전 취소는 재고에 영향을 주지 않는다.
- 조회 중에는 “불러오는 중”, 조회 실패는 “불러오지 못함”, 실제 조건에 맞는 기록이 없으면 “기록 없음”을 구별한다. 통신 실패를 기록 없음으로 보여 주지 않는다.
- 금액 내부 계산은 소수 원가를 유지한다. 표시 금액은 원 단위 반올림, 비율은 소수점 1자리, 재료량은 필요한 소수 자릿수를 유지한다. 등급은 반올림 전 비율로 판정한다.
- 기존 자료에 없는 단위 변환이나 환불·음수 판매·세금 계산은 만들지 않는다. 잘못 입력한 판매는 수정·삭제로 바로잡는다.
- 기록 변경은 프로그램 저장소에 반영한다. 원본 엑셀·JSON 파일은 수정하지 않는다. 일반 입력과 조회에서는 파일을 만들지 않으며 F10에서만 백업 파일을 생성한다.

## 6. 기능별 요구사항

### F01. 본인 확인과 접근 제한 — PRD M9

**사용 행동:** 프로그램에 접근하고 본인 확인을 완료한다.

**처리:** 허용된 본인인지 확인한 뒤에만 매장 기록을 읽거나 변경할 수 있게 한다. 화면뿐 아니라 자료 조회·저장·백업·복원 요청에도 같은 제한을 적용한다.

**결과:** 성공 시 주요 기능 메뉴를 사용한다. 실패 시 매장 기록과 수익 수치를 보여 주지 않는다. 파일 생성은 없다.

**오류·예외:** 다른 사람은 거부한다. 본인 확인이 만료되면 재확인 안내, 미저장 입력은 현재 기기에서 유지하되 저장 완료로 표시하지 않는다. 연결 실패는 다시 시도 안내. 실제 계정과 확인 방법은 구현 전에 정하며, 회원가입·직원 초대 기능은 추가하지 않는다.

### F02. 기존 자료로 시작하고 기능 이동 — PRD M1

**사용 행동:** 최초 사용 또는 재접속, 왼쪽 메뉴에서 판매·수익성·손익·재고·비용·백업/복원을 선택한다.

**처리:** 제공된 JSON의 메뉴 8개·재료 11개·레시피·가격 이력·초기재고·운영 기록을 한 번 반영한다. 이미 사용하는 자료가 있으면 원본을 다시 추가하지 않는다. Excel과 JSON 두 형식을 합치지 않는다. ID로 연결 상태를 확인한다.

**결과:** 현재 메뉴에 맞는 기능과 저장된 자료를 보여 준다. 메뉴·재료·공급사·가격 이력은 읽기만 가능하다. 별도 파일 생성은 없다.

**오류·예외:** 읽을 수 없는 자료, 중복 ID, 존재하지 않는 메뉴·재료, 잘못된 날짜·단위가 있으면 문제 목록을 제시한다. 잘못된 자료를 조용히 일부만 가져오지 않는다. 기존 기록이 있으면 샘플을 덮어쓰지 않는다. 반복적인 사용자 파일 가져오기는 2차다.

### F03. 판매 기록 조회와 등록 전 미리보기 — PRD M2

**시안 연결:** 판매 일자, 전체/매장/포장 버튼, 메뉴 필터, 초기화, 새 판매 기록 등록, 채널 버튼, 메뉴 선택, 수량 +/−, 할인 초기화, 취소·닫기.

**조회:** 날짜·채널·메뉴 조건을 선택하면 해당 판매 목록, 수량·할인·순매출 소계를 보여 준다. 채널 버튼의 괄호 숫자는 판매수량 합계이며 행 수나 주문수와 혼동하지 않도록 표시한다. 날짜를 유지한 채 초기화하면 채널은 전체, 메뉴는 전체가 된다. 목록과 소계는 같은 조건을 사용하고, 전체 날짜 요약을 함께 보이면 “선택일 전체”로 구별한다.

**등록 입력:** 판매 날짜, 기존 메뉴, 매장/포장, 판매수량, 당시 단가, 할인 총액, 결제수수료 총액. 날짜는 목록에서 선택한 날짜, 단가는 메뉴 기준가로 시작하되 수정할 수 있다. 과거 판매일의 판매가격은 가격 이력이 없으므로 운영자가 당시 금액을 확인한다. 할인은 0으로 시작한다. 수수료는 필수 직접 입력이며 없으면 0을 입력한다.

**입력 제한:** 수량은 1 이상의 정수. 단가는 0 이상의 정수 원. 할인·수수료는 0 이상의 정수 원. 할인은 수량×단가를 초과할 수 없다. 시안의 수량 999 상한과 할인 100원 단위는 업무 규칙으로 채택하지 않는다. 수량 +/−는 1개씩 변경하며 1 미만으로 내려가지 않는다.

**미리보기:** C01~C03으로 순매출·재료원가·결제수수료·재료별 예상 사용량을 보여 준다. 이는 입력값 미리보기이며 미래 손익 예측 기능이 아니다. 아직 저장되지 않았고 재고도 차감하지 않는다. 당일 전체 메뉴 매출에 따라 바뀌는 운영비 배분과 최종 평가 등급을 이 창에서 확정하지 않는다.

**오류·예외:** 메뉴·레시피·가격이 없으면 해당 오류와 수정할 값을 표시하고 등록을 막는다. 잘못된 수량을 임의로 1로 바꾸거나 초과 할인을 0원 매출로 잘라 저장하지 않는다. 단가 0 또는 전액 할인은 이유를 확인하도록 알리고 저장은 허용한다. 수수료가 매출보다 높아도 경고 후 기록할 수 있다. 조건에 맞는 기록이 없으면 소계만 0, 상태는 “기록 없음”으로 표시한다.

**파일 결과:** 없음.

### F04. 판매 등록·수정·삭제와 재고 반영 — PRD M2·M6

**사용 행동:** “판매 기록 등록 및 재고 반영”, 행의 “기록 수정”, “기록 삭제”를 선택한다.

**처리와 결과:**

| 행동 | 처리 | 화면·저장 결과 |
| --- | --- | --- |
| 등록 | 입력 검사, 중복 확인, 적용 원가와 레시피 보관, 저장, 관련 집계 갱신 | 저장된 판매 행, 수익성·등급·손익·재고 잔량 갱신. 성공 후 등록 창 닫음 |
| 수정 | 기존 값으로 창을 열고 변경 내용 검사. 변경 전후 판매를 기준으로 관련 날짜부터 재고와 집계를 다시 계산 | 기존 기록 ID 유지, 변경된 행 및 영향 결과 갱신 |
| 삭제 | 날짜·메뉴·채널·수량을 보여 주고 최종 확인. 취소 시 유지 | 확인 시 해당 판매 제거, 그 판매에 해당하는 재료 사용도 제거하여 관련 결과 재계산 |

수량·단가·할인만 바꿀 때는 기존 개당 원가를 보존한다. 수수료는 실제 기록 총액이므로 수량을 바꿨다고 자동 비례 변경하지 않고 확인 안내한다. 날짜·메뉴·채널을 바꾸면 새 조건의 레시피와 가격 이력으로 원가를 다시 산출하고 변경 내용을 보여 준다.

변경되는 날짜·메뉴·채널 조합에 기존 판매가 있으면 합치거나 덮어쓰지 않는다. 기존 행을 수정하도록 안내한다. 새 입력 창의 값은 유지한다.

판매를 저장할 때 같은 재료 차감을 별도 재고기록으로 또 만들지 않는다. 판매에서 계산한 사용량을 재고 잔량에 한 번만 반영한다. 과거 판매 수정은 그날부터 이후 잔량에도 반영하되 실측 재고 기준은 C08을 따른다.

**오류·예외:** 재고가 음수가 될 때는 예상 잔량과 확인할 재료를 보여 주고 저장을 허용한다. 저장 실패는 입력값 유지·기존 기록 유지. 재계산 불가가 예상되면 원인을 보여 주고 변경 완료로 처리하지 않는다. 다른 기기에서 해당 행을 이미 변경·삭제했으면 늦은 저장을 막고 최신 자료 확인을 안내한다. 삭제 취소는 아무 기록도 바꾸지 않는다.

**파일 결과:** 없음. 원본 엑셀·JSON은 유지한다.

### F05. 비용 기록 조회·입력·수정·삭제 — PRD M3

**시안 상태:** 비용 관리 이동 메뉴만 있다. 목록·입력 창의 상세 시안이 필요하다. “지출 결의서 추가”는 별도 결재 기능으로 구현하지 않는다.

**입력:** 비용 귀속일, 기존 8개 비용항목, 금액. 귀속일은 이 비용을 어느 날짜 손익에 포함할지 뜻한다. 금액은 0 이상의 정수 원이며 0도 명시적으로 기록할 수 있다. 새 비용의 기록 출처는 직접 입력으로 구분한다.

**처리:** 날짜와 항목으로 비용을 조회한다. 저장 시 비용 ID를 부여하고 해당 날짜 운영비·메뉴 부담·등급·일·월 손익을 갱신한다. 수정은 기존 ID를 유지한다. 삭제는 항목·날짜·금액 확인 후 수행한다. 비용 변경은 재료 잔량을 바꾸지 않는다.

**결과:** 비용 목록, 같은 조건의 비용 합계, 변경된 수익성·손익. 파일 생성은 없다.

**오류·예외:** 같은 날짜·항목의 비용은 여러 건일 수 있으므로 자동 중복 제거하지 않는다. 같은 날짜·항목·금액이 이미 있으면 중복 가능성을 알리고 별도 비용인지 확인 후 저장한다. 원자료의 배분 비용이 있는데 같은 월 비용 전체를 다시 입력하면 중복 위험을 안내한다. 음수 비용·새 비용항목은 1차에서 받지 않는다. 잘못된 비용은 수정·삭제로 정정한다. 재료 구매대금은 판매 원가와 중복될 수 있으므로 기존 운영비 항목에 넣지 않도록 안내한다. 저장·삭제 실패나 기기 간 충돌은 F04와 같은 원칙을 따른다.

월비용계획 편집·월액의 자동 일배분은 제공하지 않는다. 원래 있던 일배분 비용은 그대로 조회·수정·삭제할 수 있다.

### F06. 일별·월별 실적 및 손익 조회 — PRD M5

**시안 연결:** 일별 세부/월별 누적, 날짜 표시, 날짜·요일 검색, 손익 카드와 흐름 차트, 일자별 표, 상세 전표 조회, 입력하기.

**입력:** 조회할 날짜 또는 월. 시안의 날짜 표시 부분에는 선택 기능이 필요하다. 메뉴 수익성에서도 같은 날짜·월을 선택할 수 있도록 기간 선택을 보완한다.

**처리:** C04·C05로 선택 기간을 계산한다. 일별은 해당 날짜, 월별은 달력 월의 1일~말일 기록을 묶는다. 월을 선택하면 실제 기록 범위·미마감 날짜를 함께 표시한다. 표 검색은 현재 기간의 날짜·요일로 목록을 좁힌다. 카드의 기간 합계는 유지하고 검색된 표 소계는 별도로 표시한다.

**결과:** 판매수량, 할인 후 순매출, 식재료원가, 포장원가, 결제수수료, 비용항목별 운영비, 기록 기준 손익·이익률. 손익 흐름 차트의 금액은 카드·표와 일치한다. 시안에서 빠진 포장원가·수수료를 누락하지 않는다. 상세 전표 조회는 해당 날짜의 판매·비용 원기록을 읽기만 보여 준다. “입력하기”는 날짜를 넘겨 판매 등록으로 이동한다.

**미마감과 공백:** 원자료의 마감 여부를 표시한다. 미마감일의 저장된 판매·비용은 “입력 기록 기준” 소계로 표시하고 마감 완료 실적 소계와 구분한다. 미입력 미래일은 매출 0이 아닌 “미집계”다. 월비용계획은 실적 합계에서 제외하며 전망 금액도 만들지 않는다. 휴무일에도 날짜에 귀속된 운영비는 포함한다. 기간에 비용만 있고 판매가 없으면 비용·손실은 표시하고 매출 이익률은 산출하지 않는다.

**오류·예외:** 잘못된 월·날짜는 조회하지 않고 수정 안내. 기록 없는 기간은 “기록 없음”; 완전한 1개월로 표시하지 않는다. 가격·원가 누락은 수익 계산 불가 안내. 손실은 음수 그대로 표시하며 0으로 바꾸지 않는다. 읽기 실패 때는 마지막 조회가 과거 내용임을 표시하거나 숨기고 다시 시도 안내.

**파일 결과:** 없음. 시안 Excel 내보내기는 1차에서 실행하지 않는다.

### F07. 메뉴별 수익성·등급·상세 조회 — PRD M4

**시안 연결:** 등급별 카드, 전체/S/A/B/C 버튼, 메뉴명·분류·등급 검색칸, 메뉴 행 클릭, 상세 창의 닫기.

**처리:** 날짜·월을 선택하면 모든 메뉴의 판매·원가·수수료·운영비 부담을 C01~C07로 계산한다. 그 뒤 등급과 검색을 동시에 적용해 목록을 좁힌다. 예를 들어 S 선택 후 라떼 검색은 두 조건을 모두 만족한 메뉴만 보여 준다. 검색이 등급 필터를 지우는 현재 시안 동작은 사용하지 않는다.

**화면 결과:** 메뉴명·분류, 판매수량, 순매출, 실제 평균 판매단가, 매장/포장 판매수량 비중, 총 식재료·포장원가, 총 수수료, 운영비 부담, 총 남는 금액, 개당 남는 금액, 수익률, 평가 등급. 총액과 개당 금액을 명시해 서로 혼동하지 않게 한다. 평균 판매단가와 할인 후 개당 순매출도 구별한다.

등급 카드는 각 등급 메뉴 수와 목록을 보여 준다. 평균 수익률은 메뉴별 비율의 단순 평균이 아닌 합계 금액 기준이다. 비용을 메뉴에 나누기 전에 검색·필터로 메뉴를 제외하지 않는다. 전체 기간 합계와 현재 목록 소계를 구별한다.

**상세 창:** 선택 메뉴의 기간·판매량, 당시 가격·할인, 매장/포장별 원가, 수수료, 운영비 항목별 부담, 남는 금액, 등급 근거와 적용 기준을 보여 준다. 레시피 구성은 원자료 기준으로 읽기만 표시한다. 당일 가격 변경이 섞이면 하나의 고정 단가로 설명하지 않는다.

**오류·예외:** 판매 없는 메뉴는 “판매 없음”, 수익률·등급 없음. 순매출 0은 손익 금액을 표시하되 비율·등급은 “판정 불가”. 비용·원가 누락이나 계산 기준 불일치도 “판정 불가”이며 C등급으로 대신하지 않는다. 비용을 나눌 수 없는 날짜의 금액은 “메뉴 미배분 운영비”로 별도 표시한다. 상세 원가 구성 합계와 표 금액이 다르면 완료 결과로 내보내지 않고 계산 오류 안내. 음수 수익은 그대로 보여 준다.

**파일 결과:** 없음. 인쇄/PDF·원가표 내보내기·레시피 단가 수정·자동 경영 조언은 1차 제외.

### F08. 입고·폐기·실측 재고 기록 — PRD M6

**시안 상태:** 재고 이동 메뉴만 있다. 입력 창과 기록 목록 보완이 필요하다.

| 기록 유형 | 사용자 입력 | 처리·결과 |
| --- | --- | --- |
| 입고 | 날짜, 재료, 입고 수량. 공급사·입고 단위원가는 선택 입력 | 재료의 기준 단위로 양수 증감 저장. 재고 잔량 증가 |
| 폐기 | 날짜, 재료, 버린 수량, 사유 | 사용자는 양수를 입력하고 프로그램은 음수 증감으로 저장. 잔량 감소 |
| 실제로 센 재고 | 날짜, 재료, 실제 수량, 사유 | 해당 날짜 마감 기준 실측 수량 보관. 직전 계산 잔량과의 차이를 계산해 반영 |

날짜·재료·수량은 필수. g·ml는 0.001 단위까지, 개는 정수로 입력한다. 입고·폐기는 0 초과, 실측은 0 이상이다. 단위는 재료에 따라 고정한다. 입고 단위원가는 구매 묶음 전체의 금액이 아니라 기준 단위 1g·1ml·1개당 금액임을 알린다. 최초 가격과 가격 이력은 이 입력으로 수정하지 않는다.

실측 재고는 당일 판매·입고·폐기를 모두 반영한 마지막 수량이다. 한 날짜·재료에 한 번만 기록한다. 재고기록이 생겼다고 비용기록에 구매대금이나 폐기비를 자동 추가하지 않는다.

**화면·저장 결과:** 날짜·재료·유형·증감·실측·사유의 재고기록과 변경된 잔량·소진 상태. 입력 오류는 저장 전에 바로잡는다. 파일 생성은 없다.

**오류·예외:** 다른 단위, 음수 입력, 없는 재료·공급사, 잘못된 단위원가는 오류. 폐기 후 음수가 되면 경고 후 기록 가능. 같은 날짜·재료 실측이 이미 있으면 두 번째 실측을 새로 저장하지 않는다. 저장 실패는 기존 잔량 유지·입력값 유지. 실측 전 기록이 빠져 차이를 계산할 수 없으면 실제 수량을 확인할 수 있어도 조정 저장 완료로 처리하지 않는다.

재고기록 수정·삭제는 PRD에서 명시되지 않았으므로 별도 기능을 추가하지 않는다. 오입력된 수량은 다음 실측 재고로 바로잡을 수 있으나 원래 기록이 없어지는 것은 아니다. 이 제한이 운영에 부족하면 재고기록 수정·삭제를 별도 요청해야 한다.

### F09. 재료 잔량과 이미 떨어진 재료 조회 — PRD M6·M7

**입력:** 확인 기준일. 기본은 현재 날짜이며, 과거 날짜도 선택 가능하다.

**처리:** 초기재고부터 기준일까지 판매에서 사용한 재료와 모든 재고기록을 C08로 반영한다. 손익 화면의 월만으로 재고를 새로 시작하지 않는다. 초기재고나 실측 재고를 매월 반복해서 더하지 않는다.

**결과:** 재료명·기준 단위·기준일 잔량, 최근 실측 날짜·수량, 기준일 이후 입고는 제외한 결과, 상태. 0은 “소진”, 음수는 “소진·기록 차이 확인”, 양수는 “잔량 있음”. 음수를 0으로 숨기지 않는다. 별도로 실제로 센 수량인지 기록에서 계산한 수량인지 표시한다.

**오류·예외:** 초기재고 전 날짜는 조회 불가. 재료 사용 레시피나 단위가 없으면 영향을 받는 잔량은 “계산 불가”이며 정상으로 표시하지 않는다. 미입력 판매가 있을 수 있는 날짜는 “입력 기록 기준 잔량” 안내. 미래일은 예상 재고를 산출하지 않는다. 연결 실패는 잔량 0으로 표시하지 않는다.

**파일 결과:** 없음. 곧 부족해질 재료, 납기 기반 경보, 발주량 계산은 2차다.

### F10. 저장·여러 기기에서 같은 기록 사용·전체 백업 — PRD M8

**저장:** 판매·비용·재고 기능에서 저장을 누르면 본인의 공통 기록에 반영한다. 화면에 “저장 중/저장됨/저장 실패”를 구별한다. 성공한 기록은 다른 기기에서 조회하거나 다시 불러올 때 같은 값으로 확인할 수 있어야 한다. 실시간 POS 연결이나 즉시 자동 갱신을 약속하지 않는다.

**여러 기기 예외:** 오래 열어 둔 화면의 값이 최신이 아닐 수 있다. 동일 기록이 다른 기기에서 변경되었으면 저장 전에 충돌을 알려 최신 자료를 다시 확인하게 한다. 먼저 저장한 내용을 보존하며 늦은 입력을 자동 덮어쓰지 않는다. 통신이 끊긴 상태에서 저장 성공을 표시하거나 기기별 별도 기록으로 계속 저장하지 않는다. 미저장 입력은 현재 화면에서 유지하며 오프라인 대기열 기능은 추가하지 않는다.

**백업 행동:** 전체 백업 화면 또는 “원장 백업/백업·복원 퀵메뉴”에서 백업을 실행한다.

**처리:** 본인 권한을 확인하고 한 시점의 전체 기록을 묶는다. 메뉴·재료·공급사·레시피·가격 이력·영업달력·판매·초기재고·재고기록·비용·월비용계획·자료정보 및 채택한 계산·등급 기준을 포함한다. 조회 필터로 일부를 빼지 않는다. 계산 결과만 저장하여 원기록이 사라지게 하지 않는다.

**파일 결과:** `프렙카페_전체백업_YYYYMMDD_HHmmss.json` 다운로드. 날짜와 시각은 한국 시간. 파일에는 백업 형식 버전, 생성시각, 대상 매장, 기록 범위·수, 원기록과 계산 기준을 포함한다. 로그인 비밀번호·인증 정보는 넣지 않는다.

**화면 결과:** 생성 완료 시 파일명·백업 기준시각·포함 기록 수를 보여 준다. 사용자의 디스크에 실제 보관되었는지는 브라우저 다운로드 결과를 확인하도록 안내한다. 단순히 시간 경과 후 “저장됨”으로 바꾸지 않는다.

**오류·예외:** 읽기 또는 파일 생성 실패는 완료 표시 없이 다시 시도 안내. 다운로드 취소·차단은 파일 보관 성공으로 표시하지 않는다. 백업 중 원기록이 바뀌어도 서로 다른 시점의 판매·재고를 섞지 않는다. 본인 확인이 만료되면 백업 중단. 정기 자동 백업·백업 이력 관리·보고서 내보내기는 추가하지 않는다.

### F11. 전체 기록 복원 — PRD M8

**사용 행동:** 전체 백업·복원 메뉴 → JSON 파일 선택 → 복원 내용 확인 → 전체 교체 최종 확인.

**처리:** 파일 형식·버전·매장·필수 기록·계산 기준·날짜·단위·ID 중복·참조 연결을 검증한다. 현재 기록 수·기간과 복원할 기록 수·기간을 보여 주고 “현재 전체 기록이 백업 내용으로 교체됨”을 명시한다. 선택만으로 복원하지 않는다.

**결과:** 확인 후 전체 자료와 기준을 한 번에 교체하고 모든 실적·수익성·재고를 원기록에서 다시 계산한다. 기존 로그인 자격은 교체하지 않는다. 성공 후 복원한 기록 범위와 결과를 표시하고, 다른 기기의 열린 과거 자료로 저장하면 충돌로 처리한다. 복원 자체는 새 파일을 만들지 않는다.

**오류·예외:** JSON이 아닌 파일, 빈 파일, 깨진 파일, 지원하지 않는 버전, 다른 매장, 누락 표·기준, 중복 ID·잘못된 연결은 적용하지 않고 이유를 보여 준다. 원본 샘플 JSON은 프로그램 전체 백업과 형식이 다르므로 백업으로 가장하여 복원하지 않는다. 복원 전 현재 기록 백업을 권고하고 F10을 이용할 수 있게 한다. 자동으로 별도 백업을 생성하는 기능은 추가하지 않는다. 취소·검증 실패·쓰기 실패는 기존 자료를 유지한다. 복원 중에는 새 변경을 받지 않고 진행 상태를 표시한다. 복원 성공 전까지 일부만 새 자료인 상태를 보여 주지 않는다.

## 7. 계산 방법

이 장의 계산은 추천 채택 기준이다. 사례 숫자는 동작 이해를 위한 예시이며 실제 매장 실적이 아니다. 빠진 값을 0으로 채워 계산하지 않는다.

### C01. 판매 매출·직접 비용

- 할인 전 판매금액 = 판매수량 × 판매 당시 단가.
- 순매출 = 할인 전 판매금액 − 해당 집계 줄의 할인 총액.
- 식재료원가 = 판매수량 × 당시 개당 식재료원가.
- 포장원가 = 판매수량 × 당시 개당 포장원가.
- 직접 비용 = 식재료원가 + 포장원가 + 결제수수료 총액.
- 직접 비용 차감 후 금액 = 순매출 − 직접 비용. 최종 메뉴 수익은 여기에서 운영비 부담까지 뺀 값이다.

예: 20개×4,800원, 할인 1,000원이면 순매출은 95,000원이다. 할인은 개당 1,000원이 아니라 이 기록 전체의 1,000원이다. 수수료도 개당 금액으로 다시 곱하지 않는다.

원래 자료의 순매출·원가는 기록값을 보존한다. 최초 검증 때 수량·단가·할인으로 계산한 매출과 기록 순매출이 다르면 오류로 알리고 임의로 고치지 않는다.

### C02. 새 판매의 개당 원가

판매일 이전 또는 당일의 가장 최근 적용시작일 가격을 재료별로 선택한다.

- 재료 기준 단위당 가격 = 해당 가격 이력의 구매가격 ÷ 구매용량.
- 메뉴 개당 식재료원가 = 적용 레시피의 식재료별 사용량×단위당 가격의 합.
- 메뉴 개당 포장원가 = 적용채널이 포장인 포장재 사용량×단위당 가격의 합. 매장 판매에는 그 항목을 포함하지 않음.

현재 자료의 포장 재료는 포장컵세트 I10·디저트포장세트 I11이다. 나머지는 식재료다. 레시피 버전은 해당 판매에 저장하여 재고 사용량에도 같은 버전을 쓴다.

구매용량 0, 판매일에 적용 가능한 가격 없음, 단위 불일치, 레시피 누락은 계산 불가다. 최초구매가격이나 시안 원가로 조용히 대체하지 않는다. 새 판매 원가는 저장 시 확정해 보관하고 과거 전체 판매 원가를 현재 가격으로 다시 쓰지 않는다.

### C03. 판매에 따른 재료 사용량

재료 사용량 = 판매수량 × 해당 판매의 레시피 버전에서 메뉴 1개당 사용하는 재료량.

적용채널이 빈칸인 레시피는 모든 채널에 사용하고, 포장 전용은 포장 판매에만 더한다. 현재 자료의 라떼 20개는 원두 400g·우유 4,000ml를 사용한다. 포장이라면 포장컵세트 20개를 함께 사용한다. 시안의 원두 360g·우유 3,600ml를 사용하지 않는다.

### C04. 날짜별 매장 손익

해당 날짜의 모든 판매를 합산한다.

- 기록 기준 손익 = 순매출 합계 − 식재료원가 합계 − 포장원가 합계 − 결제수수료 합계 − 비용기록의 운영비 합계.
- 이익률 = 기록 기준 손익 ÷ 순매출 합계 × 100. 순매출 0이면 비율 없음.

운영비에는 기존 비용기록의 8개 항목을 포함한다. 월비용계획을 다시 더하지 않고, 수수료와 재료 구매대금을 운영비로 다시 넣지 않는다.

폐기·실사조정은 1차에서 수량에만 반영한다. 폐기 손실과 실사 차이의 금액 평가, 재고 자산 평가, 세금·장비 감가상각을 자동 추가하지 않는다. 따라서 이 값은 기록된 판매 원가·수수료·운영비 기준의 손익이며 현금 잔액이나 공식 회계 손익이 아니다. 이 한계를 손익 설명에 표시한다.

### C05. 기간 집계·평균·비중

- 월 금액·판매수량 = 그 월에 들어 있는 날짜별 기록 합계. 마감 완료와 마감 미확인 소계를 구분하고, 합계에는 포함 범위를 명시한다.
- 기간 이익률 = 기간 손익 합계 ÷ 기간 순매출 합계 × 100. 날짜별 비율을 평균내지 않음.
- 일평균 순매출 = 마감 완료된 영업일의 순매출 합계 ÷ 그 영업일 수. 미마감일·휴무일 제외, 해당 영업일 수 0이면 평균 없음.
- 채널 매출 비중 = 해당 채널 순매출 ÷ 전체 순매출 × 100.
- 메뉴 판매수량 비중 = 해당 메뉴 판매수량 ÷ 전체 메뉴 판매수량 × 100.
- 평균 당시 판매단가 = 할인 전 판매금액 합계 ÷ 판매수량 합계.
- 할인 후 개당 순매출 = 순매출 합계 ÷ 판매수량 합계.

분모 0이면 “산출 불가”, “판매 없음” 등 해당 이유를 표시한다. 조회 표 검색 결과로 기간 전체 비중·평균을 다시 계산하지 않는다.

### C06. 메뉴별 운영비 부담과 수익

각 날짜마다 전체 메뉴를 대상으로 계산한 뒤 월 조회에서는 결과를 합친다.

- 날짜별 비용항목의 메뉴 부담 = 그날 해당 비용항목 금액 × 그날 해당 메뉴 순매출 ÷ 그날 전체 순매출.
- 날짜별 메뉴 운영비 부담 = 비용항목별 메뉴 부담의 합. 원 단위 배분 전에는 그날 전체 운영비×메뉴 순매출 비중과 같다.
- 메뉴 총수익 = 메뉴 순매출 − 메뉴 식재료원가 − 메뉴 포장원가 − 메뉴 수수료 − 메뉴 운영비 부담.
- 개당 수익 = 메뉴 총수익 ÷ 메뉴 판매수량.
- 메뉴 수익률 = 메뉴 총수익 ÷ 메뉴 순매출 × 100.

예: 운영비 100만 원, 라떼 순매출 비중 60%라면 라떼의 운영비 부담은 60만 원이다. 검색으로 라떼만 남겨도 운영비 100만 원 전체를 라떼에 다시 부담시키지 않는다.

그날 전체 순매출이 0이면 운영비는 어느 메뉴에도 나누지 않고 “메뉴 미배분 운영비”로 둔다. 휴무일 비용도 이 원칙을 따른다. 따라서 **메뉴 총수익 합계 − 메뉴 미배분 운영비 = 매장 기록 기준 손익**이어야 한다. 이를 확인하지 않고 메뉴 합계와 매장 손익을 같다고 표시하지 않는다.

운영비를 원 단위로 배분할 때 비용항목별 총액을 보존한다. 같은 날짜·비용항목의 기록을 먼저 합친 뒤 각 메뉴의 정확한 몫을 구해 원 미만은 버리고, 남은 원은 소수 부분이 큰 메뉴부터 1원씩 배분한다. 소수 부분이 같으면 메뉴 ID 순으로 배분한다. 메뉴 부담은 이렇게 배분한 항목별 금액의 합으로 만든다. 전체 운영비를 별도로 다시 배분하여 다른 값으로 표시하지 않는다. 날짜·월과 상세 화면에서 같은 금액을 사용한다.

### C07. 평가 등급

기본 평가 기준은 다음과 같이 채택한다. 매장 운영비 부담 후의 수익률을 쓰며 재료비만 차감한 비율로 등급을 매기지 않는다.

| 등급 | 설명 | 반올림 전 수익률 조건 |
| --- | --- | --- |
| S | 우수 | 20% 이상 |
| A | 양호 | 10% 이상, 20% 미만 |
| B | 주의 | 0% 이상, 10% 미만 |
| C | 적자 | 0% 미만 |

기준은 저수익과 적자를 구분하기 위한 초기 운영 추천값이며 업계 표준이 아니다. 사용자의 추천안 위임에 따라 채택했고 시안의 60/45/30% 기준은 사용하지 않는다. 10%는 A, 20%는 S, 0%는 B다. 표시값이 반올림으로 경계를 넘더라도 판정은 원래 비율 기준이다.

판매 없음, 순매출 0, 원가·비용 정보 누락은 등급을 부여하지 않는다. 미마감 기록 기준의 등급에는 “입력 기록 기준” 표시를 붙인다. 여러 평가 기준을 고르거나 기준을 직접 편집하는 화면은 2차다.

### C08. 재고·실측 조정·소진

초기재고를 시작점으로 날짜 순서대로 반영한다.

- 실측 전 잔량 = 전날 잔량 + 당일 입고량 − 당일 폐기량 − 당일 판매 사용량.
- 실측이 없으면 위 잔량을 당일 잔량으로 사용한다.
- 실측이 있으면 조정량 = 실제로 센 수량 − 실측 전 잔량. 당일 최종 잔량은 실제로 센 수량이다.

시각 정보가 없으므로 실측은 같은 날의 모든 입고·폐기·판매가 끝난 뒤의 수량으로 해석한다. 같은 날 재료별 실측은 하나만 둔다. 원자료의 실사조정에 실측수량과 증감수량이 함께 있으면 실측수량을 한 번 반영하고 기록 증감을 추가로 또 더하지 않는다.

원자료의 증감수량은 원기록으로 보존한다. 과거 판매를 수정하면 실측 전 계산 잔량과 계산된 조정량은 달라질 수 있으나 당시 실제로 센 수량은 바꾸지 않는다. 상세에는 원기록 증감과 현재 계산된 실측 차이가 다르면 그 이유를 표시한다. 실측수량 없이 증감만 있는 조정은 기록된 증감을 한 번 적용한다.

예: 기록상 1,000ml, 실측 900ml이면 차이 −100ml이고 최종 900ml다. 이후 그날 판매를 고쳐 기록상 잔량이 950ml가 되어도 실측 900ml는 유지하고 차이는 −50ml가 된다. 실측 이후 날짜의 판매·입고·폐기 변경은 이후 잔량을 바꾼다.

잔량 = 0이면 소진, 잔량 < 0이면 소진·기록 차이 확인, 잔량 > 0이면 잔량 있음. 미입력 재고·계산 불가는 소진 0으로 취급하지 않는다. 미래 소진 시점이나 필요한 발주량은 산출하지 않는다.

## 10. 구현 완료 확인 사례

아래 사례는 개발 결과를 검사할 때 사용할 기준이다. 이 문서를 작성하며 프로그램 검사를 완료한 것은 아니다.

1. 매장 라떼 20개 등록 전 미리보기는 재고를 바꾸지 않는다. 저장 후 원두 400g·우유 4,000ml가 사용된다. 포장 판매로 바꾸면 포장컵세트도 20개 사용된다.
2. 판매수량 20개를 10개로 바꾸면 사용량이 10개분으로 바뀐다. 새 10개분을 기존 20개분에 추가 차감하지 않는다. 삭제하면 해당 판매 사용량이 제거된다.
3. 같은 날짜·메뉴·채널을 다시 등록하면 중복 저장을 막는다. 취소하면 매출·재고·파일에 변화가 없다.
4. 운영비 변경은 그날 메뉴 부담·등급·일·월 손익을 바꾸고 재고를 바꾸지 않는다. 월비용계획을 함께 더하지 않는다.
5. 메뉴 검색·등급 필터를 켜도 원래 운영비 부담은 동일하다. 메뉴 수익 합계에서 미배분 운영비를 빼면 매장 손익과 일치한다.
6. 수익률 경계 0/10/20%는 B/A/S, 음수는 C, 순매출 0은 판정 불가다. 반올림 전 기준을 적용한다.
7. 실측 900ml와 조정 −100ml가 함께 있어도 800ml로 이중 반영하지 않는다. 과거 판매 수정 뒤에도 실측 수량은 유지한다.
8. 아직 미마감인 날짜는 매출 0으로 단정하지 않는다. 비용만 있는 날짜는 기록 기준 손실과 메뉴 미배분 비용을 표시한다.
9. 한 기기에서 저장한 내용을 다른 기기에서 조회할 수 있다. 두 기기의 같은 행 변경은 먼저 저장한 값을 보존하고 늦은 저장에 충돌 안내를 한다.
10. 본인 확인 없이 기록과 백업을 얻거나 복원할 수 없다. 백업·복원 후 모든 연결 자료와 계산 기준이 같으며, 잘못된 복원 파일은 기존 기록을 바꾸지 않는다.

## 11. 남은 확인과 4시간 제약

사용자가 남은 사항을 추천대로 결정하도록 위임했으므로 현재 추가 선택 질문은 없다. 위임으로 채택한 D01~D10·계산·등급·예외 처리와 PRD 합의는 구분하여 기록했다.

외부 조건인 배포 대상·본인 계정은 실제 구현 시 확인해야 한다. 이를 임의의 서비스나 계정으로 결정하지 않는다. PRD 밖의 시안 기능은 계속 미승인 상태이며 이번 위임을 신규 기능 추가 승인으로 해석하지 않는다.

시안에 없는 비용·재고·복원·본인 확인 화면의 보완, 여러 기기 저장, 접근 제한, 운영비 배분과 등급이 모두 1차 필수 범위다. PRD의 총 240분 목표는 유지하되, 실제 구현 가능 여부는 이 작업량과 배포 조건을 확인해야 한다. 필요한 기능을 조용히 삭제하거나 완료하지 않은 저장·복원을 완료로 표시하지 않는다. 4시간에 맞추기 어렵다면 줄일 범위 또는 추가 시간을 사용자와 별도로 합의한다.
