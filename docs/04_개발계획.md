로컬 검사 환경은 사용자가 별도로 승인했다. 이는 운영용 Supabase 기술 변경이나 운영 연결 검사 완료를 뜻하지 않는다. 사용자 확인 결과는 `docs/05_테스트결과.md`에 기록하고, 사용자 확인 없이 EPIC을 완료로 표시하지 않는다.

EPIC 1의 로컬 기능은 사용자 확인을 모두 통과해 완료로 표시했다. Story 1.1~1.4의 로컬 구현·검사·화면 확인 범위에 해당하며, Supabase 인증·저장 연결과 GitHub 보관·Vercel 배포 검사는 별도 미완료다. 운영 준비까지 포함한 EPIC 전체 완료를 뜻하지 않는다. EPIC 2·3은 이번 작업에서 착수하지 않았다.

기준 문서: `docs/01_PRD.md`, `docs/02_FRD.md`, `docs/03_TRD.md`와 `design` 폴더의 시안. 기능·사용 순서·계산 기준은 이 문서들에서 정한 내용을 유지한다.

## 전체 작업 순서와 나눈 이유

전체 작업은 **① 판매를 실제로 저장 → ② 비용을 반영해 수익성·손익 확인 → ③ 재고 확인과 전체 복원** 순서로 진행한다.

**총 3개 EPIC, 14개 Story**다. EPIC은 화면에서 확인할 수 있는 큰 작업 묶음, Story는 사용자가 한 가지 목적을 달성하는 기능 단위다.

| 순서 | EPIC | Story 수 | 나눈 이유 |
| --- | --- | ---: | --- |
| 1 | 본인 접속과 판매 기록 관리 | 4 | 분석에 필요한 원기록과 안전한 저장을 먼저 완성 |
| 2 | 수익성·손익 확인과 기록 보관 | 5 | 판매·비용을 연결해 계산하고, 여러 기기 사용과 백업 확인 |
| 3 | 재고 관리와 전체 복구 | 5 | 판매에 따른 잔량을 확인하고, 모든 기록을 복원하는 흐름 완성 |

각 Story에는 화면, 실제 저장, 필요한 계산과 오류 처리를 함께 구현한다. 계산·저장 기반 작업은 해당 Story의 개발 작업에 포함하며, 화면만 만드는 별도 완료 항목으로 분리하지 않는다.

## EPIC 1. 본인 접속과 판매 기록 관리

**포함 Story:** 1.1~1.4  
**완료 기준:** 본인만 접속하고, 제공 자료를 조회하며, 판매 등록·정정 결과가 새로고침 후에도 유지된다. 판매 원가와 재료 사용량도 실제 자료로 계산된다.

### Story 1.1. 본인 계정으로 안전하게 접속한다

- **사용자가 할 수 있는 일:** 본인 계정으로 로그인하고 로그아웃한다.
- **자동 검사:** 비로그인·다른 계정의 화면과 직접 서버 요청을 차단한다. 로그인 만료 시 저장을 막고, 비밀키가 화면 코드에 포함되지 않았는지 검사한다.
- **화면 확인 행동과 예상 결과:** 로그인 전 업무 주소를 열면 기록이 보이지 않는다. 본인 로그인 후 메뉴를 사용할 수 있고, 로그아웃하면 다시 접근할 수 없다.

### Story 1.2. 기존 판매 기록을 찾아본다

- **사용자가 할 수 있는 일:** 제공 자료로 시작하고 날짜·메뉴·매장/포장 조건으로 판매를 조회한다.
- **자동 검사:** 초기 자료의 개수·연결·중복을 검사한다. 재접속해도 자료가 다시 추가되지 않고, 목록과 소계가 같은 조건을 사용하는지 확인한다. 조회 실패와 기록 없음도 구분한다.
- **화면 확인 행동과 예상 결과:** 날짜와 채널을 바꾸면 해당 판매만 표시된다. 초기화하면 날짜를 유지하면서 메뉴·채널 조건이 해제된다. 시안의 예시 메뉴가 아닌 제공 자료의 메뉴가 나온다.

### Story 1.3. 새로운 판매를 기록한다

- **사용자가 할 수 있는 일:** 날짜·메뉴·채널·수량·단가·할인·수수료를 입력하고 미리보기 후 저장한다.
- **자동 검사:** 당시 가격 적용, 식재료·포장원가, 순매출과 사용량을 검사한다. 빈 필수 값·할인 초과·중복 판매는 저장되지 않는다. 연속 클릭·통신 실패로 중복 저장되지 않고, 취소는 기록을 바꾸지 않는다.
- **화면 확인 행동과 예상 결과:** 검사용 날짜에 라떼 20개, 단가 4,800원, 할인 총액 1,000원을 입력하면 순매출은 **95,000원**이다. 재료 사용량은 원두 **400g**, 우유 **4,000ml**이고, 포장이면 컵세트 **20개**가 추가된다. 저장 후 새로고침해도 기록이 남는다.

### Story 1.4. 잘못된 판매 기록을 바로잡는다

- **사용자가 할 수 있는 일:** 기존 판매를 수정하거나 잘못 등록한 판매를 확인 후 삭제한다.
- **자동 검사:** 수량 변경 시 사용량을 중복 차감하지 않는다. 수량·단가·할인 수정은 기존 개당 원가를 보존하고, 날짜·메뉴·채널 변경은 FRD대로 다시 산출한다. 수수료는 자동 비례 변경하지 않는다. 수정·삭제 실패는 기존 기록을 유지한다.
- **화면 확인 행동과 예상 결과:** 라떼 20개를 10개로 수정하면 해당 판매의 사용량은 원두 **200g**, 우유 **2,000ml**로 바뀐다. 삭제를 취소하면 유지되고, 확인하면 목록에서 사라진다. 이후 분석·재고 화면에서도 같은 변경이 반영된다.

## EPIC 2. 수익성·손익 확인과 기록 보관

**선행 조건:** EPIC 1  
**포함 Story:** 2.1~2.5  
**완료 기준:** 비용 변경이 메뉴 수익성·등급·일·월 손익에 반영되고, 다른 기기에서 같은 기록을 확인할 수 있다. 실제 전체 백업 파일을 내려받을 수 있다.

### Story 2.1. 운영 비용 기록을 관리한다

- **사용자가 할 수 있는 일:** 기존 비용항목으로 비용을 등록하고, 잘못된 금액을 수정하거나 삭제한다.
- **자동 검사:** 필수 값·음수 금액·중복 가능 경고를 검사한다. 월비용계획을 비용기록에 다시 더하지 않는다. 변경 결과가 저장되며 재료 잔량은 바뀌지 않는다.
- **화면 확인 행동과 예상 결과:** 검사용 날짜에 광고비 10,000원을 추가하면 그날 비용 합계가 **10,000원 증가**한다. 5,000원으로 수정하면 증가분도 5,000원이 되고, 삭제하면 이전 합계로 돌아간다.

### Story 2.2. 메뉴별 수익성과 평가 근거를 확인한다

- **사용자가 할 수 있는 일:** 날짜·월별로 운영비 부담 후 남는 금액과 등급을 보고, 검색·등급 필터·상세 내역으로 판단 근거를 확인한다.
- **자동 검사:** 날짜·비용항목별 순매출 배분, 잔여 원 처리, 소수 원가, 등급 경계를 검사한다. 검색해도 운영비 부담은 바뀌지 않는다. 판매 없음·0매출·자료 누락은 판정 불가로 구분한다.
- **화면 확인 행동과 예상 결과:** 라떼만 검색해도 검색 전과 같은 운영비 부담이 표시된다. 등급 필터와 검색이 함께 적용된다. 상세 창에서 재료·포장·수수료·운영비와 남는 금액을 확인한다. 검사용 수익률 **0%·10%·20%는 B·A·S**, 음수는 C로 나온다.

### Story 2.3. 일별·월별 매장 실적과 손익을 확인한다

- **사용자가 할 수 있는 일:** 날짜 또는 월을 선택하고 실적·손익·비용 구조와 원기록을 확인한다.
- **자동 검사:** 식재료·포장·수수료·운영비가 각각 한 번만 반영된다. 일·월·카드·표·차트의 합계가 일치하고, 메뉴 수익 합계에서 미배분 운영비를 빼면 매장 손익과 같다. 미마감·휴무·기록 없음·0매출도 검사한다.
- **화면 확인 행동과 예상 결과:** 일별에서 월별로 바꾸면 실제 집계가 바뀐다. 매출이 없는 날에도 비용은 손실로 표시된다. 미마감 날짜는 매출 0이 아닌 미집계 또는 입력 기록 기준으로 나온다. 표를 검색해도 기간 전체 합계와 검색 소계를 구분할 수 있다.

### Story 2.4. 다른 기기에서 같은 기록을 이어서 사용한다

- **사용자가 할 수 있는 일:** 컴퓨터에서 저장한 기록을 휴대폰에서 조회하고 이어서 수정한다.
- **자동 검사:** 두 기기의 같은 기록 수정, 오래된 화면의 삭제, 저장 응답 유실을 검사한다. 먼저 저장한 내용이 유지되고, 늦은 저장은 충돌 안내를 받는다. 기기별 별도 기록을 만들지 않는다.
- **화면 확인 행동과 예상 결과:** 컴퓨터에서 판매를 저장하고 휴대폰에서 다시 조회하면 같은 값이 나온다. 두 기기에서 같은 행을 열어 각각 수정하면 먼저 저장한 값이 남고, 두 번째 기기에는 최신 기록 확인 안내가 나온다.

### Story 2.5. 전체 기록을 백업 파일로 보관한다

- **사용자가 할 수 있는 일:** 전체 기록과 계산 기준을 JSON 파일로 내려받는다.
- **자동 검사:** 모든 원기록·기준정보·계산 설정이 같은 시점으로 포함된다. 필터가 백업 범위를 줄이지 않고, 로그인 정보·비밀키는 제외된다. 파일 생성 실패·접근 거부·전송 제한도 검사한다.
- **화면 확인 행동과 예상 결과:** 메뉴 필터를 켠 상태에서도 전체 백업이 생성된다. 안내된 파일명으로 실제 JSON을 내려받고, 기록 범위·개수를 확인할 수 있다. 다운로드가 차단되면 보관 성공으로 표시하지 않는다.

## EPIC 3. 재고 관리와 전체 복구

**선행 조건:** EPIC 1·2  
**포함 Story:** 3.1~3.5  
**완료 기준:** 판매·입고·폐기·실측이 연결된 잔량과 소진 재료를 확인한다. 백업으로 전체 기록을 복원하고, 수익성·손익·재고가 복원 전 백업 시점과 일치한다.

### Story 3.1. 기준일의 재료 잔량과 소진 상태를 확인한다

- **사용자가 할 수 있는 일:** 날짜를 선택해 재료별 잔량, 최근 실측, 이미 떨어진 재료를 확인한다.
- **자동 검사:** 초기재고부터 기준일까지 판매·재고기록을 한 번씩 반영한다. 과거 판매 수정·삭제, 실측 기준, 0·음수·계산 불가를 검사한다. 미래 잔량을 예측하지 않는다.
- **화면 확인 행동과 예상 결과:** 판매 등록·수정·삭제 전후의 잔량이 해당 사용량만큼 바뀐다. **0은 소진**, 음수는 **소진·기록 차이 확인**으로 나오며, 자료 부족은 0 대신 계산 불가로 표시된다.

### Story 3.2. 재료 입고를 기록한다

- **사용자가 할 수 있는 일:** 재료와 입고 수량을 기록해 잔량에 반영한다.
- **자동 검사:** 날짜·재료·기준 단위·양수 수량과 선택 항목을 검사한다. 중복 클릭은 한 번만 저장되고, 실패하면 기존 잔량을 유지한다. 구매대금을 비용에 자동 추가하거나 가격 이력을 바꾸지 않는다.
- **화면 확인 행동과 예상 결과:** 우유 1,000ml를 입고하면 해당 날짜 이후 잔량에 반영된다. 이후 실측이 없는 구간에서는 기존 잔량보다 **1,000ml 증가**하고, 새로고침 후에도 입고 기록이 남는다.

### Story 3.3. 버린 재료를 기록한다

- **사용자가 할 수 있는 일:** 폐기한 재료의 수량과 사유를 기록한다.
- **자동 검사:** 양수로 입력한 폐기량이 음수 증감으로 저장된다. 단위 오류·빈 사유·잘못된 수량은 차단한다. 음수 잔량은 경고하되 FRD대로 기록할 수 있고, 손익에 폐기비를 자동 추가하지 않는다.
- **화면 확인 행동과 예상 결과:** 우유 폐기량을 **200ml**로 입력하면 기록에는 감소로 표시되고 잔량이 200ml 줄어든다. 잔량이 음수가 되어도 0으로 숨기지 않는다.

### Story 3.4. 실제로 센 재고를 반영한다

- **사용자가 할 수 있는 일:** 당일 마지막에 센 실제 수량을 기록해 기록상 잔량과 차이를 확인한다.
- **자동 검사:** 같은 날짜·재료의 실측 중복, 음수 실측, 증감과 실측의 이중 반영을 검사한다. 과거 판매를 수정해도 당시 실측수량은 유지되고 계산 차이만 바뀐다.
- **화면 확인 행동과 예상 결과:** 기록상 우유 1,000ml에 실측 **900ml**를 입력하면 차이는 **−100ml**, 최종 잔량은 **900ml**다. 이후 과거 판매를 정정해도 실제로 센 900ml는 유지된다.

### Story 3.5. 백업으로 전체 기록을 복원한다

- **사용자가 할 수 있는 일:** 백업 파일을 선택하고 내용을 확인한 뒤 현재 전체 기록을 교체한다.
- **자동 검사:** 파일 버전·변조 여부·매장·필수 자료·연결·단위·계산 기준을 검사한다. 취소·실패는 기존 자료를 유지하며, 성공 후 원기록과 계산 결과가 일치한다. 복원 직후 다른 기기의 오래된 저장도 차단한다.
- **화면 확인 행동과 예상 결과:** 백업 후 판매·비용·재고를 변경하고 백업을 복원하면 백업 시점의 기록과 수익성·손익·잔량으로 돌아간다. 파일 선택만으로 교체되지 않는다. 깨진 파일이나 원본 샘플 JSON은 거부되고 기존 자료가 남는다.

## 모든 Story에 적용할 완료 조건

자동 검사는 계산뿐 아니라 실제 검사 환경의 저장소와 서버, 브라우저 동작까지 확인한다. 화면 확인용 숫자는 별도 검사 환경에 저장한 원기록에서 계산하며, 화면에 고정 숫자를 넣어 통과시키지 않는다.

각 Story는 다음 조건을 모두 충족해야 완료다.

- 정상 동작과 기본 오류·취소·저장 실패를 검사한다.
- 저장 성공은 새로고침 후에도 확인되고, 실패는 성공으로 표시되지 않는다.
- 본인 접근 제한과 휴대폰 사용을 확인한다.
- 해당 단계에서 구현한 화면 간 결과가 일치한다. 이후 화면이 추가되면 연결 검사도 다시 수행한다.
- 시안의 제외 기능과 가짜 완료 알림을 제품 동작으로 채택하지 않는다.

GitHub 코드 보관, 검사 환경과 운영 환경 분리, Vercel 배포는 각 EPIC의 개발·검증 작업에 포함한다. EPIC마다 검사 환경의 실제 화면으로 확인하고, 최종 운영 배포는 전체 흐름과 백업·복원 검사까지 통과한 뒤 진행한다.

PRD의 **총 4시간 목표는 유지**하지만, 이 Story 구성이 완료 시간을 보장하지는 않는다. 시간이 부족해도 계산·저장·오류 처리·검증을 생략하거나 필수 기능을 임의로 제외하지 않는다.
